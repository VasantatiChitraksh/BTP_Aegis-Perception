AEGIS / RESTORMER EDGE HANDOFF
============================
Scope
-----
Frozen Restormer best checkpoint (epoch 51), plus frozen official YOLOv8n COCO
weights. No retraining, dataset split changes or detector finetuning. The
deployment graph remains unpruned. Separate pruning experiments are documented
in docs/restormer_compression.txt; they do not replace this graph.
Restoration graph: batch 1, RGB [-1,1], 256 high x 448 wide. Aspect-preserving
bilinear resize, bottom/right edge padding, remove padding, clip/round, resize
back to original dimensions. Detector: RGB [0,1], centered 640x640 letterbox,
COCO IDs person=0, bicycle=1, car=2, motorcycle=3, bus=5, truck=7.
This is a proposed operating point, not a claim that Restormer is real-time.
The full native-resolution restoration benchmark is a different experiment.

What is measured locally
------------------------
ONNX vs PyTorch agreement on four restoration images (one per weather),
three YOLO images and matching YOLO decoding/NMS. Real CPU pipeline execution.
A fixed 72-image DAWN engineering pilot (24/weather, filename-hash selection)
compares raw / resize-only / Restormer inputs with the same YOLO weights.
The full 704-image annotation set is audited separately. Neither pilot nor
DAWN has smoke road-object annotations. The pilot does not establish general
ADAS performance, statistical superiority or deployment safety.
Read the generated report and JSON for actual outcomes; a completed restoration
training run does not guarantee that restoration improves object detection.

Hardware status
---------------
No Jetson was accessible. TensorRT compilation, FP16/INT8 accuracy, Jetson RAM,
latency, sustained thermal behaviour, camera compatibility and power consumption
are NOT measured here. A CPU result must never be labelled Jetson FPS.
The target scripts support TensorRT 8.5/8.6 and 10.x, typically JetPack 5/6 Orin
installations. They reject other API generations rather than silently guessing.
An original Jetson Nano is not an Orin Nano; its older stack may be unsupported.
No power modes, system packages or driver settings are changed automatically.

On the Jetson
-------------
1. Copy and extract artifacts/releases/aegis_restormer_edge_20261024.tar.gz.
   Verify the supplied .sha256 before extracting; enter the extracted directory.
2. Use JetPack's TensorRT/CUDA/OpenCV, with a venv that can see system packages:

   python3 -m venv --system-site-packages .venv
   .venv/bin/python -m pip install -r configs/deployment/edge_runtime_requirements.txt
   export AEGIS_PYTHON="$PWD/.venv/bin/python"
   bash scripts/deployment/edge_device.sh prepare

   Do not pip-install desktop CUDA/TensorRT over JetPack. If cv2 is absent,
   install the JetPack-compatible python3-opencv package through the OS.
   A missing python3-venv package must also be installed through the OS first.
3. Engine compilation and validation run sequentially, with 512 MiB maximum
   builder workspace per engine. This is NOT a cap on total process/GPU RAM.
   Close memory-heavy applications, especially on 4 GB devices. Compilation
   can need more memory than steady-state inference; failures are logged.
   Engines are hardware/software-specific: rebuild after JetPack/TRT changes.
4. Run paired sustained throughput measurements:

   bash scripts/deployment/edge_device.sh benchmark

   Each mode processes 300 frames from the three supplied real-image samples,
   after 20 warmup calls. JSON records elapsed throughput and median/p95 times;
   tegrastats is captured if installed. The benchmark excludes rendering and
   camera capture. Frame timing includes file I/O except first-frame decode.
   results/device_comparison.csv and .json collect completed measured runs.
   Record the physical device, RAM, storage, cooling, power mode and ambient
   conditions alongside the results. Keep power mode identical across modes.
5. Camera or video (choose raw or restored explicitly):

   "$AEGIS_PYTHON" scripts/deployment/edge_run.py \
     --restorer engines/restormer_fp16.engine --detector engines/yolov8n_fp16.engine \
     --source camera:0 --mode restored --max-frames 300 --save-visuals \
     --output results/camera_trial_01

   Replace camera:0 with a video path or a camera index. USB/V4L2 is expected;
   CSI cameras may need a separately configured GStreamer capture source.
   No infinite capture queue: frames are processed synchronously. Saved video
   uses source FPS metadata; actual throughput is reported in benchmark.json.
   This is an experimental perception demo, not vehicle control software.

Precision gates and fallback
----------------------------
FP16 is mixed precision: sensitive Restormer reductions, softmax, matrix
multiplication, elementary arithmetic and normalization are constrained to FP32.
Convolutions may use FP16. Runtime I/O remains FP32. No speedup is assumed.
Candidate engines must produce finite outputs and pass the four-weather fixture
checks: restoration RMSE <=0.004 and max error <=0.05 on [-1,1], each sample
PSNR drop <=0.1 dB and SSIM drop <=0.001 against clean targets at resized geometry.
FP32 uses tighter numerical tolerances. These are initial engineering acceptance
limits, not a comprehensive accuracy guarantee. YOLO gates raw box/score outputs.
A failed candidate is not renamed to an approved engine. Read .rejected.json.
If FP16 fails, build FP32 with a NEW filename using edge_build.py --precision
fp32, and use that filename in edge_run.py. Do not weaken gates just to pass.

Optional INT8 experiment, AFTER the FP16 baseline works
-----------------------------------------------------
   "$AEGIS_PYTHON" scripts/deployment/edge_build.py \
     --onnx artifacts/edge_v1/exports/256x448/restormer/restoration.onnx \
     --fixtures artifacts/edge_v1/exports/256x448/restormer/fixtures.npz \
     --calibration artifacts/edge_v1/exports/256x448/restormer/calibration.npz \
     --kind restormer --precision int8 --output engines/restormer_int8.engine

This uses 64 training-only inputs (16 per weather, background round-robin), not
random tensors or validation/test images. TensorRT performs entropy calibration;
there is no calibration-cache reuse across runs. Sensitive math stays FP32 and
unsupported INT8 operations may use FP16/FP32: the engine is not uniformly INT8.
Passing the small fixture gate is only a first check. Compare quality and
annotated detection on a larger untouched set before adopting it. YOLO INT8 is
not enabled: restoration inputs are not an appropriate detector calibration set.
Pruning is not applied to the deployment graph: zeroing weights does not by
itself shrink this dense graph or prove faster Jetson inference. The separate
compression screen tests disposable pruning copies without recovery training.
The compression bundle adds edge_compression_device.sh to compare FP32, FP16
and INT8 sequentially; see docs/restormer_compression.txt for that experiment.

Reproduce local evidence in the main repository
----------------------------------------------
   .venv/bin/python scripts/deployment/edge_export.py
   .venv/bin/python scripts/deployment/edge_detector_export.py
   .venv/bin/python scripts/deployment/edge_prepare_fixtures.py
   .venv/bin/python scripts/deployment/edge_dawn.py all
   .venv/bin/python scripts/deployment/edge_dawn.py all --full

The last command is OPTIONAL full evaluation (several CPU hours), separately
stored in dawn_full704/detection_full704. It resumes completed images/evaluations
only when contracts match. Keep frozen test metrics out of model selection.
DAWN source TXT IDs are COCO ID+1; every class and box is checked against VOC XML.
Only derived labels are corrected; original annotations remain untouched.
Full 80-class COCO names are used in evaluation; six road IDs are filtered.
One annotated train object is outside this six-class scope and is documented.
The views use lossless PNG and identical image geometry to avoid JPEG artifacts.
Report precision/recall are at max-F1 confidence; mAP uses conf=.001, IoU=.7 NMS,
max_det=300. Live visualization defaults to confidence .25 and is not mAP.
